# Turbo Pascal 5.5 oracle probes

These small programs are compiled with the user-provided Turbo Pascal 5.5 distribution and run under DOSBox-X. They capture source behavior for cases used by the shared engine compatibility work without including Turbo Pascal binaries in the project.

The full verifier compiles the shared LibZoo flood-fill routine and extracts the Android editorFloodFill/editorCopyTile JNI functions plus production placement/preparation/paste adapters into a host WASM harness. All four Pascal editor maps (EDITORFL, EDFLDOVR, EDFLDQ17, and EDFLDFUL) pass against the shared queue implementation. EDPLACE.PAS directly calls nested Pascal EditorPlaceTile for pattern placement, protected-player handling, plain clipboard tile paste, and refusal at MAX_STAT when pasting a copied stat; all four outcomes match extracted production adapter outputs. EDSTAT.PAS compares no-script paste plus script-bearing Bomb copy/paste: it copies a source TStat record, mutates a raw source script byte after assignment, then checks that BoardPrepareTileForPlacement/AddStat pastes the aliased data byte-for-byte, including CR and NUL. This matches the Android JNI clipboard's shallow script pointer and the extracted paste adapter. Board draw/removal callbacks remain doubles; remaining editor mutations, editor UI, and Android device JNI execution remain outside this differential.

`OOPCHAR.PAS` calls the original `OopExecute` with a non-default P1 glyph for -32768, -1, 0, 1, 127, 255, 256, and 32767. `compare-oop-char.js` compares P1, Cycle, and instruction cursor against libzoo's production dispatcher, confirming that only 1 through 255 replace P1 and `#CYCLE` after `#CHAR` on the same line is skipped.

`OOPPUT.PAS` and `compare-oop-put.js` compare eight direct `#PUT` placements against production, including each edge direction. This preserves the source bounds: the rightmost column and row 24 are writable, while column 61 and row 25 are excluded; rejected placements leave the observed edge tile unchanged.

`OOPCHG.PAS` and `compare-oop-change.js` compare the complete 61-by-26 tile map after `#CHANGE EMPTY SOLID`. All 1,497 matching cells, the scan's interior limits, untouched nonmatching elements, and retained colors match the production dispatcher. The fixture keeps the player stat aligned with the player tile so the source's damage path is represented consistently.

`OOPFLAGS.PAS` and `compare-oop-flags.js` compare every byte in Pascal's ten 21-byte flag slots after duplicate clears, first-empty-slot reuse, duplicate suppression, and setting a new flag with all ten slots full. The comparison includes stale short-string tail bytes and confirms full-table `#SET` overwrites slot ten.

OOPSEND.PAS and compare-oop-send.js compare compiled Pascal and production label sends for positive self-lock bypass, negative in-world event lock enforcement, lowercase object/label source text, and continued search past a locked duplicate target. The parsed `#SEND` cases pass the live stat `DataPos` by reference as the game does: self-send dispatches during the same `OopExecute` call, and cross-send records the recipient's byte-8 entry point and `DataPos=-1` after its `#END`.

EDITORFL.PAS directly calls the original nested `EditorFloodFill` for a bounded 3-by-3 area; EDFLDOVR and EDFLDQ17 cover a 792-cell byte-counter-wrap corridor and a dense 17-by-17 region. EDFLDFUL.PAS checks a 58-by-23 open interior, all 1,334 filled cells, and the complete 60-by-25 board map. These editor probes allocate `IoTmpBuf` before `WorldCreate`, matching ZZT startup. A startup-faithful capped diagnostic plus three fresh run-only DOSBox-X runs all recorded 1,334 changed cells, 2,588 iterations, and 2,587 queue writes; earlier run-only timeouts came from a temporary harness that omitted that startup allocation.

DOORPRB.PAS directly exercises Pascal's black-key and colored-door touch handlers. It confirms that an unchecked Keys[0] read sees the high byte of Gems, black-key pickup adds 256 while preserving the low byte, duplicate pickup leaves the second key, and regular door colors 1 through 7 require and consume only their matching key.

ITEMPRB.PAS checks ordinary and overflowing ammo, gem, score, and health counters on the active-game path. Pascal wraps its signed 16-bit ammo/gem/score counters; after the gem increments negative health, GameUpdateSidebar clamps the result to zero while GameStateElement is E_PLAYER.

ENERGYPR.PAS checks the active-game Energizer touch against the reconstructed source: the tile is cleared without changing its color, EnergizerTicks becomes 75, the 112-byte priority-9 sound pattern is queued, the one-time message is stored, the ALL:ENERGIZE label is sent to the target Object, and the touch deltas remain unchanged.

TORCHPR.PAS checks both first-time and repeat Torch pickups. It covers signed 16-bit counter wrap, tile/color preservation, message timer insertion and suppression, the one-time message flag, the priority-3 sound bytes, and unchanged touch deltas.

BOMBPRB.PAS checks the first contact that arms a bomb, including P1, tile/color, activation message and timer stat, sound priority/bytes, and unchanged deltas. It also checks that later contact pushes an active bomb into an empty tile and leaves it in place when blocked by a normal wall. Five direct tick cases cover idle, alternating beep, final warning/radius change, detonation/removal, and negative-fuse no-op; `compare-bomb-tick.js` checks stat/tile/sound state against production and caught the conditional-pointer `sizeof` bug that appended a NUL byte to the beep.

TERRAIN.PAS captures Invisible, first/repeat Forest, first/repeat Fake, and Water touch behavior: resulting elements/colors, one-time messages and flags, message timer ticks, sound priority/bytes, and unchanged deltas. It locks in the Fake wall's 150-tick message duration.

DAMAGE.PAS captures player damage at health 15 and 5, the GameUpdateSidebar zero clamp, Ouch message timer, and full sound priorities/bytes. Its Slime touch case verifies stat removal, the Breakable tile/color, and that the damage sound outranks Slime's lower-priority scrape.

PASSAGE.PAS builds two boards and touches a Passage into the target board. Two passages share the requested color, so the output verifies Pascal's last-match scan order, player/start coordinates, clearing the old spawn tile, timer reset, pause state, zeroed movement deltas, and exact transition sound bytes.

BOARDENT.PAS runs the reconstructed BoardEdge touch handler for all four neighbor directions, including the rule that west/east entry keeps the player's current row. It also checks blocked-entry rollback and a destination that already contains the player, recording board/player state, movement deltas, start coordinates, time reset, and pause state.
BOARDIN.PAS calls the original `BoardEnter` directly for a lit board, a first dark-board entry, and a repeated dark-board entry. It checks player spawn capture, board-time reset, the one-time torch hint, and the message-timer stat and text; the production C regression exercises the same entry cases.
SOUNDTIK.PAS invokes the original `SoundTimerHandler` body through a test-only wrapper in the isolated staged `SOUNDS.PAS`. It checks a one-byte pattern, an odd three-byte pattern, a complete note/duration pair, and a zero-duration byte that wraps the counter from 0 to 255 and delays the following note until tick 257. The wrapper removes the interrupt directive and avoids installing a DOS timer vector only in the probe build, making each timer step deterministic.
`SOUNDCLK.PAS` invokes the original `SoundHasTimeElapsed` routine with a deterministic test-only `GetTime` shim in the staged `SOUNDS.PAS`. It compares threshold edges, zero-duration behavior, the 59.99-to-00.01 minute rollover, counter retention on a false result, and modulo behavior after a backward clock step against production `zoo_has_hsecs_elapsed` in seven cases. Only the clock source is injected; the Pascal elapsed-time routine itself is unchanged.
`ZEROSPD.PAS` runs the original `GamePlayLoop` for five zero-speed cycles. The verifier adds a stop counter only to its staged `GAME.PAS` copy; no wait or gameplay logic is replaced. `compare-zero-speed-loop.js` matches the Pascal cycle count, current-tick delta, stat phase, PIT time, and elapsed counter against the production `zoo_tick` harness.
INTEGPRB.PAS replays the original paused GamePlayLoop: two buffered right keys push a boulder twice, and two interacting objects run #GIVE GEMS 1 / #IDLE and #GIVE AMMO 1 / #IDLE over six zero-speed cycles. Output-only hooks in the staged GAME.PAS copy capture L0 loaded state, S0 loop start, T1 pause-to-play, C1-C6 cycles, T2 post-save, T3 post-reload, and F0 final state. Snapshots include the normalized player/monitor role, world/stat/scheduler/input fields, tile sentinels, RNG words, the full live-stat pointer-alias matrix, unique script bytes, and sound queue fields/bytes. The clean differential matched 41,690 fields across 12 checkpoints (3,473 at L0/S0/T2/T3/F0 and 3,475 at T1/C1-C6), plus two logical sound events / 20 fields and nine ordered cell writes / 36 fields. The generated 961-byte `.SAV` matches at all 565 stable fresh-world positions; 396 undefined/pointer positions are classified (327 differ, 69 happen to match). Both implementations then load the exact Pascal-generated `.SAV`: Pascal `WorldLoad=true` matches production `zoo_world_load=0`, and the round-trip `.SAV` matches 949 preserved bytes while classifying only 12 process-specific stat pointer bytes. The probe seeds only the undefined `TWorldInfo.unk1` word to zero. The verifier now compiles `INTEGPRB` in one DOSBox-X session and runs it in a fresh session; combining compile/run inherited compiler allocation history and terminated before capture, so the isolated run standardizes the probe environment. This remains one prototype, not one of the ten required fixtures. Pascal `WorldSave` failure-path outcomes, broader transitions, and the full ten-fixture corpus remain open under E2-10.
BOARDENC.PAS fills the original 60×25 board with one tile and calls `BoardClose`. It captures the resulting length-prefixed board record, then calls the original `WorldSave` to write a full `.ZZT`. `compare-pascal-boardenc.js` checks the board record through shared LibZoo's `.BRD` parser/export and compares the full Pascal `.ZZT` against the production `zoo_board_close` plus `zoo_io_world_write` path. The `.ZZT` differential matches all 25,928 bytes; the board record round-trip matches all 289 payload bytes. The first experiment compared the Pascal `World.BoardData` bytes with LibZoo's packed internal board representation (289 versus 261 bytes); those are different representations and that result is intentionally excluded from compatibility evidence. The actual file-boundary comparison passes. This covers one valid save scenario, not the full four-format serialized-field and boundary matrix. The direct source RLE trace confirms five 255-cell runs followed by a 225-cell run.
BRDALI.PAS loads the source-produced DEMO world, finds a board with script data and a later stat, then makes the later stat share the earlier script pointer and calls the original `BoardClose`. It records the resulting negative wire `DataLen` reference in `ALIAS.BRD`, reopens that board through Pascal `BoardOpen`, and makes a further stat share the same pointer. The chained case proves the source loop's last-match behavior: stat 3 references stat 2 with wire `DataLen=-2`, while stat 4 references stat 3 with wire `DataLen=-3`. It then calls original `BoardOpen` on the final serialized chain and directly checks that stats 2, 3, and 4 all resolve to the same 98-byte script block. `compare-pascal-brd-alias.js` checks this Pascal pointer topology against the shared LibZoo parser, then compares both full 2,025-byte records through production import/export (4,050 bytes total). Numeric Pascal data-pointer bytes remain opaque preserved record bytes, not host-pointer equality evidence; see the direct evidence note for the record hashes and clean-run details.
BOARDDEC.PAS calls the original `BoardOpen` on two synthetic board records. It verifies zero-count byte underflow to a 256-cell run and confirms that a final run extending past cell 1,500 does not move the following board-info byte.
BOARDRLE.PAS calls the original `BoardOpen` for each possible 8-bit run count from 0 through 255, writes every decoded tile plus the following `MaxShots` byte, and compares the complete 256-record binary trace with the production reader.
WORLDTIT.PAS calls the original `WorldLoad` with `titleOnly=true` on a fixture whose header declares multiple boards but contains only board 0. It checks successful loading, `BoardCount=0`, `CurrentBoard=0`, `IsSave=true`, and a present first board.

FULLLOAD.PAS calls full `WorldLoad` on a fixture that declares 15 boards but contains only board 0, with `CurrentBoard=0`. The probe clears missing board slots first so the DOSBox run is reproducible; it confirms Pascal accepts the absent trailing board-length records, keeps `BoardCount=15`, leaves `IsSave=false`, opens the complete current board, and captures the full current-board record after the original `BoardClose`. The production differential runs `zoo_world_load` and `zoo_world_save`, then compares the on-disk board record byte-for-byte (1,135 bytes). It separately records the tested `GetMem(0)` pointer-presence result, which differs from production's null zero-length buffers. In ordinary Pascal startup, unread lengths and payload bytes can come from stale allocator memory, so the exact malformed-board state is not portable; opening an absent board remains unverified.

NEGLEN.PAS calls full `WorldLoad` on a one-board fixture whose stored length word is `0xFFFF` and whose payload occupies 65,535 bytes. It succeeds with `BoardLen[0]=-1`, confirming that Turbo Pascal passes the signed integer to word-sized `GetMem` and `BlockRead` arguments as an unsigned 65,535-byte count.

NEGBRD.PAS follows the original editor `.BRD` import sequence with a `0xFFFF` length header, allocates and reads the full 65,535-byte payload, then opens the board. Its `negative-brd 1 -1` output confirms that `.BRD` uses the same unsigned `Word` count conversion as world-board records.

BRDIOPRB.PAS probes empty and one-byte length words plus declared four-byte payloads with 0, 1, 2, or 3 bytes available through the original `BlockRead` calls. The length read reports I/O error 100 and the next `IOResult` is 0; an empty header preserves the seeded `$1234`, while one input byte replaces only its low byte (`$1202`). Short payload reads report error 100 and leave the unread suffix at its explicitly seeded `$A5` values. This suffix observation is direct Pascal evidence for this probe setup, not a universal file-format value.

`BRDXFER.PAS` executes the original nested `EditorTransferBoard` through `EditorLoop` with a controlled import choice, filename, and error-dialog Escape. The staged `GAME.PAS` changes only the `TextWindowSelect` call into that Escape input; file reads, `DisplayIOError` `IOResult` calls, both import branches, `BoardCreate`/`BoardOpen`, and redraw/cleanup remain reconstructed source routines. The six-case direct differential covers an empty header, a one-byte `SHORTHD.BRD` header, and declared length-4 payloads with 0, 1, 2, or 3 payload bytes. Incomplete payloads reach `BoardCreate` and produce `board 0 255 0 4 31 30 12 0 0 0 0 0`; all eight selected fields match production. The empty-header case reopens the prior board with `BoardLen=319`; seven comparable fields plus its name and all four neighbor links match, excluding LibZoo's private internal buffer length of 321 (+2 metadata bytes). The one-byte `$03` header reopens it with Pascal `BoardLen=259`; eight fields, name, and neighbors match. Production's truncated-record parser separately rejects incomplete headers and payload sizes 0–3 with `ZOO_ERROR_INVAL`; the Pascal unread-payload suffix has no corresponding production buffer and is not compared. Earlier uncontrolled corrected-fixture attempts and the invalid nine-character `SHORTHEAD` fixture remain excluded. See [`2026-11-27-e2-02-pascal-brd-truncation-matrix.md`](../compatibility/evidence/2026-11-27-e2-02-pascal-brd-truncation-matrix.md) for exact outputs/hashes and [`2026-11-27-e2-02-short-header-controlled-reopen.md`](../compatibility/evidence/2026-11-27-e2-02-short-header-controlled-reopen.md) for the original intervention record.
